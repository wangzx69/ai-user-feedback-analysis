# AI驱动的游戏用户反馈分析流水线

> 从公开评论采集 → 数据清洗 → LLM智能分析 → 可视化报告，全链路自动化的用户反馈分析系统

---

## 一、项目概述

### 一句话介绍

基于Python + Playwright + LLM API + ECharts搭建的游戏用户评论自动化分析流水线，以《原神》TapTap评价页为数据源，实现了从原始评论到业务洞察报告的全链路自动化，30分钟内完成146条评论的情感分析、主题分类、痛点提取与可视化报告生成。

### 核心指标

| 指标 | 数值 |
|------|------|
| 采集评论 | 200条原始 / 146条有效 |
| 平均评论长度 | 359字 |
| LLM分析准确率（情感） | 83% |
| LLM分析准确率（主题） | 93%（Prompt优化后） |
| 全流程耗时 | ~15分钟 |
| 人工干预 | 仅初始验证环节 |

---

## 二、业务背景与目标

### 为什么做这个

游戏运营团队每天面临大量玩家评论，人工阅读效率低、分类主观、难以规模化。本项目验证了**"LLM + 自动化流水线"能否替代人工完成用户反馈初筛**，并在过程中积累了可迁移的方法论。

### 要证明的能力

1. **数据采集能力**：能从真实网站抓取非结构化数据
2. **数据清洗能力**：能处理脏数据、噪音、格式问题
3. **Prompt Engineering能力**：能设计有效的LLM分析指令
4. **效果评估能力**：能量化AI输出的质量，而非盲目相信
5. **业务洞察能力**：能从数据里得出可执行的建议
6. **工程化能力**：能把以上环节串成自动化流水线

## 四、核心模块详解

### 4.1 数据采集：Playwright动态爬虫

**目标**：从TapTap评论页自动滚动加载，采集用户评论正文、用户名、评分。

**遇到的问题与解决**：

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 页面打开但采不到评论 | CSS选择器太泛，匹配到了页面其他元素 | 调整选择器，精确到评论卡片容器 |
| 浏览器自动关闭 | TapTap反爬机制检测到自动化 | 加入手动验证等待环节，设置headless=False |
| 滚动不触发新内容加载 | 页面懒加载机制 | 模拟人类滚动节奏，每次滚动后等待2秒 |
| 点进"展开"后跳转详情页 | 点击展开按钮会跳转到评论独立页 | 去掉点击展开逻辑，直接提取页面已加载的完整文本 |

**关键设计**：
- 按用户名去重，同一用户只保留一条
- 过滤<50字的短评论（无分析价值）
- 过滤乱码、键盘敲击、广告等无效内容

### 4.2 数据清洗：规则化质量过滤

**清洗规则**（按执行顺序）：

1. **去重**：按用户名去重，一个用户只保留一条
2. **去前缀**：切掉"玩过"、游戏时长前缀等非评论文本
3. **去回复**：切掉其他用户回复区混入的内容
4. **去尾巴**：切掉末尾的"展开 6 2026/7/"等UI残留
5. **长度过滤**：保留>50字的评论
6. **质量过滤**：
   - 去掉连续重复字符>8字（键盘敲击）
   - 去掉广告/引流内容
   - 去掉纯表情/无意义字符

**清洗效果**：200条原始 → 146条有效，平均359字

### 4.3 LLM分析：Coze工作流 + Prompt Engineering

**工作流设计**：
```
输入评论文本（---分隔）→ 拆分单条 → 循环调用LLM → JSON汇总 → 生成运营周报
```

**Prompt优化过程**（核心亮点）：

**第一版**：单标签分类，主题九选一
- 问题：一条评论涉及多个主题时，LLM只能选一个，导致主题准确率仅47%

**第二版（优化后）**：
1. **多标签分类**：主题改成数组输出，一条评论可标注多个主题
2. **主题定义**：为每个主题写了明确的判定标准（如"抽卡保底：讨论抽卡概率、保底机制、歪不歪、原石获取"）
3. **Few-shot示例**：提供3个标注示例，让LLM理解标注边界
4. **结构化输出**：强制JSON格式，字段明确

**优化效果**：
| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 情感准确率 | 83% | 83% |
| 主题准确率 | 47% | **93%** |
| 双项全对率 | 43% | **83%** |

### 4.4 效果评估：人工标注基准集

**为什么要评估**：不能盲目相信AI输出，必须量化准确率。

**评估方法**：
1. 从146条评论中随机抽取30条
2. 人工标注标准答案（情感+主题）
3. 对比Coze分析结果，计算准确率
4. 分析误差来源

**评估结果**：
- 情感判断准确率：83%（大方向判断可靠）
- 主题分类准确率：93%（多标签优化后）
- 误差主要来自：边缘案例（4星偏正面/中性）、多主题评论的主主题判定

**这是项目最有价值的环节**——证明你不是"调API"，而是知道怎么评估AI的好坏。

### 4.5 可视化报告：业务洞察输出

**报告结构**（参考游戏行业用户反馈报告标准）：

1. **分析概览**：KPI卡片（总评论数、平均评分、正面占比、覆盖主题数）
2. **整体口碑**：情感分布饼图 + 情绪分布柱状图
3. **主题深度分析**：
   - 主题热度排行
   - 每个主题的正/中/负面分布
   - 代表性评论（不同用户、长评论、可展开全文）
4. **核心痛点TOP5**：按出现频次排序
5. **优先级行动建议**：P0/P1/P2三级，带影响分析
6. **核心结论**：3句话总结整体口碑、主要痛点、用户画像

## 五、业务洞察（从数据中发现）

### 整体口碑
- 正面评论占比56%，负面20%，中性24%
- 平均评分4.2星，整体口碑良好

### 三大核心痛点
1. **剧情无法跳过**（P0）：老玩家回坑、新玩家赶进度都受影响
2. **抽卡体验**（P1）：歪率高、原石获取少是核心负面来源
3. **移动端优化**（P2）：低端机卡顿、发热、闪退

### 用户画像
- 老玩家占比高，对游戏有感情但对运营细节不满
- 新手/回归玩家体验友好，但长草期留存是挑战
- 玩家最在意的是"被尊重"——剧情长度、福利多少都体现了官方是否重视玩家时间

## 六、可迁移性

这套流水线不是只适用于原神。换游戏只需要改三个配置：

| 配置项 | 示例（原神） | 示例（王者荣耀） |
|--------|-------------|-----------------|
| 数据源 | TapTap app_id=168332 | TapTap app_id=37848 |
| 主题体系 | 抽卡保底/剧情角色/深渊战斗... | 匹配机制/英雄平衡/皮肤美术... |
| 领域术语 | 圣遗物/深渊/原石 | 段位/铭文/匹配机制 |

### 可迁移的场景
- 电商评论分析（淘宝/京东）
- App Store用户反馈分析
- 社交媒体舆情监控
- 客服工单自动分类

## 七、小红书版本验证（跨行业迁移）

为了验证这套框架的可迁移性，我用**同一套流水线**做了第二个项目——小红书评论内容风险分析。

### 原神版本 vs 小红书版本对比

| 维度 | 原神版本（游戏） | 小红书版本（内容合规） |
|------|-----------------|----------------------|
| 数据源 | TapTap游戏评论 | 小红书面膜类评论 |
| 分析目标 | 用户口碑分析（情感/主题/痛点） | 内容风险识别（合规/营销/引流） |
| 分类体系 | 9个游戏主题 | 6种风险类型 |
| 输出 | 运营周报 | 风险审核报告 |
| 核心能力 | 产品运营分析 | 内容治理/审核 |

### 小红书版本核心指标

| 指标 | 数值 |
|------|------|
| 分析评论 | 51条 |
| 高风险 | 9条（17.6%） |
| 中风险 | 17条（33.3%） |
| 无风险 | 17条（33.3%） |
| 风险识别类型 | 站外引流/虚假宣传/代理招募/软广推广 |

### 小红书版本亮点

1. **违规话术库**：整理TOP10常见违规话术，可直接做成关键词拦截系统
2. **P0/P1/P2分级**：不是简单标风险，而是按处理优先级排序
3. **正常用户vs营销号对比**：发现真实用户会说缺点，营销号只会说好话
4. **行动建议带预期效果**：每条建议都有数据支撑和预期提升

### 迁移成本

从原神版本到小红书版本，**只改了两个地方**：
1. Prompt里的分类体系（从游戏主题改成风险类型）
2. 报告模板（从运营周报改成风险审核报告）

爬虫、清洗、API调用、可视化框架完全复用，迁移成本<1天。

## 八、项目亮点

**1. 不是跑Demo，而是完整工程**
从数据采集到可视化报告全链路自动化，不是只调了个API。

**2. 有效果评估，不是盲目相信AI**
构建了30条人工标注基准集，量化准确率到83%/93%，知道AI哪里准、哪里不准。

**3. Prompt Engineering有数据支撑**
不是凭感觉改Prompt，而是通过对比实验（47%→93%）证明优化有效。

**4. 业务思考，不是技术自嗨**
输出不是图表堆砌，而是P0/P1/P2优先级建议，直接对应业务决策。

**5. 可迁移方法论**
证明这套流程能复用到其他游戏、其他行业，不是一次性的玩具。
